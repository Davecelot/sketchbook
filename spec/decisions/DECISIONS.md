### SB-0122 · 2026-11-17 · Component APIs speak the canonical vocabulary; no aliases
**Status:** proposed
**Supersedes:** SB-0078
**Context:** This supersedes SB-0078 in part: its "contracts keep their code names" and its alias list; the vocabulary, A1 and the design-file naming stand. SB-0078 kept the shadcn/ui code names behind aliases in `spec/api.json`, so code said `variant="default"`, `size="sm"`, `checked`, `error`, `invalid`, `open`, `value-change` while contracts, patterns and the design file said `primary`, `small`, `selected`, `errorMessage`, `validation`, `expanded`, `change`. Check A1 warned on 36 props, 3 events and 31 state keys. The package is not published yet, so a rename breaks no consumer.
**Decision:** Every component's public API uses the canonical names of `spec/api.json`, and no component prop, event or state key needs an alias (`aliases` keeps only `field-set.legend`, an element's label content): size `medium | small | large | tiny` (+ `icon-*`), variant `primary | secondary | tertiary | ghost` (Toggle and ToggleGroup `ghost | tertiary`), `selected` (Checkbox, Switch, Toggle; Toggle's `change` detail `{ selected }`), `readOnly`, `errorMessage` (attribute `error-message`), `validation` (`none | error`, Field, InputGroup), `expanded` (Collapsible, SidebarProvider; Dialog keeps `open`), `selection` (Accordion, ToggleGroup), events `change` (Accordion, Tabs) and `sb-toggle` (Collapsible, SidebarProvider), Button slots and parts `leading-icon` / `trailing-icon` (the anatomy names `icon-start` / `icon-end` stay: they name the design-file layers and token lookups), Typography `kind`, Alert `feedback` (`neutral | danger`). The three SB-0078 proposals (Toggle variants, Alert feedback, Typography kind) are confirmed. A state key is canonical as the kebab-case title or a key listed in `states.canonicalKeys` (`Focus`: `focus-visible`, the keyboard-focus `:state()` hook, and `focus-within`). Token names keep their steps (`button.height.sm`); `recipes.mts` maps canonical values to them (`tokenStep`). Extensions (`destructive`, `link`, `line`, `type`, …) stay.
**Why:** One name per idea in code, contracts, patterns and the design file; the alias count was debt that only grew harder to pay once the package ships.
**Watch out:** UI and theme still follow shadcn/ui, the API names do not: a shadcn example needs its names translated (`variant="outline"` is `tertiary`). Item and Empty media's no-box look reads `primary`. A consumer of a pre-release build must rename attributes and listen for `change` / `sb-toggle`.

### SB-0121 · 2026-11-17 · The design file may bind a spacing-scale step where the styles multiply the unit
**Status:** accepted
**Context:** ToggleGroup's gap is `calc(var(--sb-toggle-group-spacing-unit) * spacing)`; Onboarding uses `spacing="2"` (separate items) since the Nov 15 reflow fix. A design-file gap binds one variable and variables cannot multiply, so the set could only draw the joined bar, and check T4 refuses a contract token the styles do not use. Every spacing preset (`harness/standards/spacing.json`) is linear: step N is N x base and `space.unit` is step 1.
**Decision:** A library recipe may bind a step of the spacing scale (`space.N`) where the component's styles compute `space.unit x N`, and only for the pairs listed in `SCALE_BINDINGS` (`harness/lib/design/recipes.mts`, today `toggle-group: space.2`). ToggleGroup gets a design option `Spacing` (`0 | 2`, contract `$extensions["design.figma"]`): `0` is the joined bar, `2` draws separate items with every corner and border and the gap bound to `space.2`. FG9 (bindings are contract tokens) and FG12 / `parityOf` (bound tokens are styled) accept exactly those pairs; FG16 proves both looks.
**Why:** The value is exact in every brand (the scale is unit x N by construction), and nothing else in the drawn library leaves the component's own tokens.
**Watch out:** A custom spacing scale that is not linear breaks the equality; a new spacing value drawn in the file needs its step added to `SCALE_BINDINGS` and to the option's values.

### SB-0120 · 2026-11-16 · Gates run locally, not on GitHub Actions
**Status:** accepted
**Context:** `.github/workflows/ci.yml` (PR #18) ran on every PR and every push to main: checks on Node 22 and 24, and a Playwright job. By mid-November it had used 90% of the 2,000 free Actions minutes in the month. The owner wants the project to cost $0.
**Decision:** The workflow is removed and Actions is turned off for the repository. Every push runs the fast gates in `.githooks/pre-push`: the checks, the maintainer checks, `test:harness`, `typecheck` and `lint`. Before a merge, the owner runs `npm run verify` on a clean tree. It is the former CI list: check, harness tests, typecheck, the stale-output diff, lint, npm audit, the static Storybook and the component specs.
**Why:** Same gates, no hosted minutes. Splitting them keeps each push fast and saves the Storybook and Playwright minutes for the merge.
**Watch out:** Only the local Node and OS run now. Node 22 and Linux are no longer covered, and Linux CI is where #18 found a Dialog width assumption that macOS overlay scrollbars hid. Before a release, run `npm run verify` once under Node 22. `git push --no-verify` skips the hook; nothing on the server catches it.

### SB-0119 · 2026-11-16 · The harness is TypeScript, compiled in place
**Status:** accepted
**Context:** The components are strict TypeScript, but the harness (about 18k lines of `.mjs`: CLI, checks, generators, adapters, tests) is untyped and reads untyped JSON (contracts, brand config, tokens) in 62 files. Node's type stripping cannot run the installed CLI (it skips `node_modules`, and Node 22.12 to 22.17 needs a flag); 21 harness files locate the engine root and their data by a path relative to their own file.
**Decision:** Harness and `scripts/` sources are `.mts`, compiled by `tsc` (`scripts/build-harness.mjs`, `tsconfig.harness.json`) next to the source: `x.mts` becomes `x.mjs`, so every `import './x.mjs'`, `bin`, hook and doc path stays valid while `.mjs` and `.mts` files coexist during the migration. While a `.mts` still imports a hand-written `.mjs`, `tsc` (with `allowJs`) emits into `node_modules/.cache` and only the output of each `.mts` is copied next to its source, so the `.mjs` is never overwritten. A generated `.gitignore` per tree lists exactly the compiled outputs; a `.npmignore` makes the package ship them and not the sources; `harness/` also ships each module's `.d.mts`, so a project's `#harness/*` imports are typed. The Claude hooks (`.claude/hooks/`, `.claude/skills/*/hooks/`) compile the same way, and `settings.json` runs each through the hand-written launcher `.claude/hooks/run.mjs`: a fresh clone builds once on the first hook, and without output or sources a guard blocks the edit (exit 2) instead of letting it through. The build runs before `npm run check`, `generate`, `test:harness` and `sketchbook`, and in the pre-commit hook; there is no install-time script (B15). Types for JSON come from `spec/schemas` (`generated/types/`). The tool configs are TypeScript too (`prettier.config.ts`, `.storybook/*.ts`), so `engines` is `^22.18 || >=24`, where every supported Node strips types natively; `eslint.config.js` stays JavaScript with `// @ts-check`, type-checked by `npm run typecheck`, because ESLint 10 loads a `.ts` config only through jiti or an unstable flag (`docs/simplicity-debt.md`). Check H2 (source repo only: it skips where there is no `scripts/build-harness.mjs`) fails on any `.mjs` under `harness/`, `scripts/` or the hook folders that no `.mts` beside it compiles, except an allowlist kept in the check with a reason each: `scripts/build-harness.mjs` (bootstraps the build), `.claude/hooks/run.mjs` (the launcher), and `harness/lib/design/compare-runtime.mjs` and `harness/adapters/design/figma/verify-runtime.mjs` (inlined byte for byte into Figma scripts). Tests BH1 to BH8, H-L1 to H-L3 and the H2 case in `checks.test.mts` prove the pipeline.
**Why:** Types stop whole classes of errors at build time, but they are erased at runtime; compiling in place keeps the engine working from `node_modules`, with no loader, on every supported Node, and with no path rewrites.
**Watch out:** Running `node harness/...mjs` directly after editing an `.mts` uses stale output until `npm run build:harness`; a fresh clone has no compiled output until its first `npm run` of one of those scripts. Replaces the "compile to `dist/`" wording of the migration plan. A new hand-written module fails H2 until it is converted or allowlisted.

### SB-0118 · 2026-11-16 · Modal surfaces wrap Tab inside the page
**Status:** accepted
**Supersedes:** SB-0102
**Context:** This replaces only SB-0102's Watch out on native Tab and on a manual screen-reader pass; the rest of SB-0102 stands. SB-0102 accepted the native modal's Tab behavior: from the last control, focus may pass through the browser's own controls before coming back. The Sidebar drawer already wrapped with its own script. In the stable review of the overlays the owner asked for every remaining finding to be fixed at the source, this one included. SB-0102 also asked for a manual screen-reader pass, which SB-0113 replaced with automated screen-reader views.
**Decision:** Dialog and the Sidebar drawer keep Tab inside the page: Tab from the last control goes to the first, Shift+Tab from the first goes to the last. Both use one helper, `src/utils/focus-wrap.ts`. It lists the tabbable elements and treats focus inside a component's shadow root as focus on its host, so a slotted sb-input or the Dialog's built-in close button counts. The native modal still provides the top layer, the inert page, Escape and focus restore. Screen-reader checks for these components are the automated views and the Chromium accessibility tree (SB-0113), not a manual pass.
**Why:** The APG modal pattern and the reference wrap inside the page. One helper keeps the two overlays identical, and the next overlay can reuse it. Accepted by the owner on 2026-11-16.
**Watch out:** The helper wraps only at the ends; between them the browser's own order applies. The tabbable list is read again on every Tab press, so content whose tabbability changes stays current. A control that handles Tab itself and calls preventDefault keeps it.

### SB-0117 · 2026-11-15 · A page written from the components gets its outline checked when it is written
**Status:** accepted
**Context:** Value benchmark round 6: Sonnet built a settings page from sb-* components in 10 of 10 runs, and all 10 failed axe `page-has-heading-one` (3 also `landmark-one-main` and `region`). The Card contract already says to put a real heading inside sb-card-title; 7 sessions read it and ignored it. No run ran `sketchbook check`: they built the page and stopped, so a check they must remember to run does not reach them.
**Decision:** A PostToolUse hook on Edit, Write and MultiEdit (`.claude/hooks/page-outline.mjs`) reads the written file when it is `.html` or `.htm`, a full document (`<html` or `<body`) and uses at least one `<{prefix}-` element (prefix from `harness.config.json`, default `sb`). HTML comments are ignored. It requires a level-1 heading (`<h1`, or `role="heading"` with `aria-level="1"`) and a main landmark (`<main` or `role="main"`); on a miss it exits 2 with what to do and the axe rule ids, which Claude Code shows to the agent; otherwise it is silent. It ships in the Claude layer like the guard hooks. Approved by the owner on 2026-11-15.
**Why:** The gate fires at the moment the page is written, with no step for the agent to remember, and the message names the exact fix. Silent on success, it adds nothing to the always-on context (H1).
**Watch out:** It is a static check, not axe: it does not render the page, see shadow DOM, heading order or landmarks other than main, and a heading or main built by script is missed. It runs only in Claude Code sessions with the Claude layer installed; other agents, editors and CI do not run it. A fragment (no `<html` or `<body`) is never checked.

### SB-0116 · 2026-11-14 · A check never runs code the project brought, and an upgrade never overwrites without a yes
**Status:** accepted
**Context:** The project scan found that check H1 ran every hook command in the project's `.claude/settings.json` through `sh -c` with the full environment to measure its output, so `sketchbook check` or the pre-commit hook in a cloned, untrusted project ran that project's shell. `sketchbook upgrade --from <folder>` replaced harness-owned files, local edits included, without asking, while a git URL needed `--yes`. The package also ships its build tools as runtime dependencies.
**Decision:** H1 runs a hook only when it is `node "${CLAUDE_PROJECT_DIR}/.claude/<hooks|skills>/..."` on a file identical to the engine's copy, as `node <file>` (no shell) with only `PATH`, `HOME` and a scratch `CLAUDE_PROJECT_DIR`. Any other hook is not run and is reported as not measured. A folder upgrade that would write refuses without `--yes`, like a git URL, and lists the files. The build tools stay runtime dependencies: the package is the engine plus a reference library, and an app depends on the team's own package, which `init` creates with `lit` only (README).
**Why:** A check is something people run on code they have not reviewed (a fresh clone, a pre-commit hook); measuring context is not worth executing it. One confirmation rule for every upgrade source, with git as the undo. Splitting the package would cost a repository restructure for the minority who install the reference components directly.
**Watch out:** A team's own hooks still add to the always-on context but H1 no longer counts them: leave room in `contextBudget`. Editing a shipped hook makes it unmeasured until it matches the engine again.

### SB-0115 · 2026-11-14 · Link components drop script URLs from href
**Status:** accepted
**Context:** The project scan found eight elements that render a native `<a>` from an `href` prop (button, badge, item, breadcrumb link, pagination link, previous and next, sidebar menu button), bound straight into the template. Lit does not sanitize URLs, so an app that passes a user-supplied link renders `javascript:` as a script sink.
**Decision:** Every `href` goes through `safeHref()` (`src/utils/safe-href.ts`). It drops `javascript:`, `vbscript:` and `data:` URLs after removing the tab, newline and control characters browsers ignore inside a scheme, renders the `<a>` without `href`, and logs a console warning naming the URL. Every other value passes unchanged. A behavior spec per element proves a script URL is not rendered.
**Why:** A blocklist of the script-capable schemes closes the XSS sink without breaking legitimate links (`sms:`, `ftp:`, app schemes such as `slack:`) that an allowlist would refuse. This matches how React 19 and Angular treat `javascript:` URLs.
**Watch out:** A blocked link stops being a link: it leaves the tab order, which is visible in development through the warning. This is defense in depth, not a substitute for the app validating the URLs it stores. A new element that renders `href` must use `safeHref()` too.

### SB-0114 · 2026-11-13 · The Claude layer stays within +50% of a bare session
**Status:** accepted
**Context:** The value benchmark measured the Claude layer at about 16.7k tokens of fixed context per session and +18% to +88% cost per task over files plus the CLI, with QA depth as its only measured gain. The hammock hooks injected the whole skill at session start, on every prompt and in every subagent; every rule loaded in every session; review-rangers spawned 4 to 6 full agents per review.
**Decision:** The harness costs at most +50% per task over the same task with files and the CLI only. Always-on context is small and stable: hooks inject a short card once (session start, resume, clear, compact, subagent start), never per prompt; task-specific rules load by `paths:`; skill descriptions stay at most 400 characters; rarely used skills are slash-only. Agent briefs declare a model, and review committees are sized by risk. Check H1 enforces the description cap, the brief model and a byte budget for always-on context (`harness.config.json` `contextBudget`); `docs/research/value-benchmark/scripts/fixed-context.mjs` measures it, with one ablation arm per layer.
**Why:** Cost is the main pain point of the harness, and the measured overhead bought nothing outside QA depth. Anthropic's guidance and the upstream skills hammock came from (ponytail, caveman) inject once and load the rest on demand.
**Watch out:** A scoped rule is in context only once a matching file is read; skills that start such work name the rule so it still applies. The budget is bytes, a proxy; the benchmark is the real measure and should be rerun after a large change to the Claude layer.

### SB-0113 · 2026-11-13 · Screen-reader checks are automated as stored views of Chrome's accessibility tree; no manual pass
**Status:** accepted
**Context:** Command, Dialog and Sidebar each recorded a manual screen-reader pass (VoiceOver, NVDA) as owed before beta. The owner decided passes will not be run by hand and asked for an automated check across the whole harness. Playwright's own `ariaSnapshot` walks the DOM: it misses the accessible description, the modal state, `aria-activedescendant` and focus, and it lists the page behind a modal dialog, which a screen reader cannot reach.
**Decision:** The screen-reader view is read from Chrome's computed accessibility tree over the DevTools protocol (`screenReaderView` in `playwright/helpers/a11y.ts`): roles, names, descriptions, values and the announced states, after two frames so the tree is current. `aria-current` is read from the element, since the protocol has no property for it. Two layers store views as reviewable text: every story of every component and kit (`playwright/tests/screen-reader/stories.spec.ts`, views beside each component's spec in `__screen-reader__/stories/`, so `sketchbook add` carries them), and, for every component whose contract binds a key that changes what is announced, a behavior-spec test that presses those keys (`expectScreenReaderView`). Both fail on an unnamed control. Check S1 enforces it offline for every shipped component. The manual passes owed by Command, Dialog and Sidebar are replaced by these views.
**Why:** It covers what a manual pass mostly catches (name, role, state, description, focus, the active item, what a modal hides) on every change, in every project, with no screen reader installed.
**Watch out:** It is Chromium's tree only, and it is not speech: wording, verbosity, double speech, announcement timing and position in set ("2 of 3", absent from the protocol) are not checked. Speech-level tests (Guidepup driving VoiceOver or NVDA) stay an option for the composite widgets. A changed view is a review item, not an automatic pass: read the diff before `--update-snapshots`.

### SB-0112 · 2026-11-13 · A doc grid wraps into bands when a variant does not fit its cell
**Status:** accepted
**Context:** Review of Components · Overlays: the States grids of Dialog (Open: a 512 surface on its backdrop, 544) and Sidebar (Open: a 256 panel plus the trigger, 288) gave every column an equal share of the card, and the wide variants were cropped or overflowed, against SB-0091.
**Decision:** The blueprint gives each grid the fixed width of its widest variant (`drawnWidth`: width tokens, paddings and gaps; text, fill-width layers and nested instances count as nothing). The Figma adapter keeps as many columns per band as leave that width inside the cell padding (`matrixColumns`), and the grid draws band after band, each with its own head row; the verify expects the cells in that order. A grid that fits keeps one band, so the other docs draw as before. Fit-to-cell (SB-0090) still applies to components that reflow.
**Why:** A grid stays readable and complete at doc width without shrinking an example below its own width.
**Watch out:** The width is a lower bound from the default density; a variant wide only through its text or a nested instance is not seen, and a variant wider than one full-width column still takes the cell's width.

### SB-0108 · 2026-11-12 · Composite pitfalls found reviewing Command
**Status:** accepted
**Context:** The Command review (review-rangers, LOW: no blocker, accessibility risks) found pitfalls that will recur in every composite that filters slotted children or links roles across shadow roots (Select, Combobox, Menu, Sidebar).
**Decision:** (1) Element-reference ARIA (`ariaActiveDescendantElement`, `ariaControlsElements`) fails silently where unsupported, so a component that depends on it warns once in the console and its contract states the browser floor. (2) axe sees a combobox-to-listbox link only through an ID, so element-reference links need a scoped, counted exemption in the behavior spec, never a blanket rule filter. (3) A parent that re-filters on child changes must observe property sets too: child props it reads are reflected, and the observer includes `characterData` when text is a fallback value. (4) A focus design that moves the indicator to an active option must keep a visible indicator on the field when no option is active (WCAG 2.4.7).
**Why:** Each failure is invisible in a default run: the tests pass in Chromium, axe passes with the filter, and a framework setting properties never triggers the observer.
**Watch out:** Behavior specs for these composites read state with `expect.poll`, not one-shot evaluates, and keep one axe test per story; under load one-shot reads and multi-story tests time out.

**Status:** accepted
**Context:** Re-pointing semantic tokens at the brand was hard-coded (primary, destructive, control heights), ran only on `init`, and skipped missing tokens silently. Light and dark were told apart by `modes[0]` in one place and the name `light` in another.
**Decision:** `spec/tokens/brand-links.json` (template in `harness/templates/`) lists each semantic token that follows brand.config and its rule: `{from: "color", role, part}` for role colors, `{from: density|radius|motion|elevation|icons|z, role}` for the rest. `harness/generators/links.mjs` applies it on every `tokens:generate` (so `init` gets it too). A link whose semantic token or foundation target is missing is reported by the generator and as a G1 warning. Modes are `"light"`, `"dark"` or `{name, role}`; the role (light or dark, default: dark only for a mode named dark) picks ramp steps and the `prefers-color-scheme` block. A mode without a template starts from its role's template. Role colors move to the nearest ramp step whose readable foreground meets the text target.
**Why:** One declarative place for "what follows the brand"; teams unlink a token by deleting its entry instead of fighting a script. Every regenerate leaves the semantic layer consistent with the config.
**Watch out:** A linked token edited by hand is overwritten on the next regenerate (G1 flags it as stale first); delete its link to own it. `semantic-brand.mjs` and its exported `applyBrandToSemantic` are gone.

### SB-0024 · 2026-11-08 · Foundations come from a standards catalog; brand.config v2 picks presets
**Status:** accepted
**Context:** Most foundations were tables inside `foundation.mjs` (mono font, weights, line heights, letter spacing, shadows, motion, z, opacity, borders, sizes), `baseSize` was ignored under the default scale, radius had three fixed styles and accents other than danger did nothing.
**Decision:** `harness/standards/<family>.json` holds 19 preset families (spacing, typeScale, lineHeight, letterSpacing, weights, rampMethods, neutrals, semanticRoles, contrast, radius, elevation, motion, density, layoutGrid, breakpoints, iconSizes, zIndex, opacity, borderWidth); each preset has id, label, values, description in our words, source URL and `verified`. `harness/standards/resolve.mjs` turns brand.config into concrete values: every foundation key is optional and accepts a preset id, `{preset}`, `{custom}` and fine overrides merged over the preset. brand.config v2 adds `typography.mono/lineHeights/letterSpacing/weights/source`, `color.roles`, radius `base`/custom px, `elevation`, `motion`, `density` objects, `contrast.preset`, `grid`, `breakpoints`, `icons`, `z`, `opacity`, `border`. Only the OKLCH ramp method is implemented; the others are catalogued as future. The v1 config keeps working and the default config produces byte-identical outputs (golden test `harness/test/golden/tokens.default.css`).

**Watch out:** Spacing keys are multipliers of the base (space.4 = 4 x base), so an 8 px unit doubles every distance. Presets marked `verified: false` are our own or approximations; their source is a pointer, not a copy. `typography.source` is recorded only; fonts.css comes later.

### SB-0017 · 2026-11-08 · The element and CSS prefix is rebrandable

### SB-0012 · 2026-11-08 · Radio Group: native radios, the group owns the semantics
**Context:** Each ds-radio-group-item renders a native radio in its own shadow root, so the browser sees every radio as a group of one.

### SB-0009 · 2026-11-08 · Shadow-DOM controls: what crosses the boundary and what doesn't
**Context:** The review-rangers review and the parity audit of Spinner, Button and Input (reports in docs/parity-audits/) found three shadow-DOM gaps, each reproduced in Chromium.
**Decision:** (1) Form controls handle Enter themselves and call `form.requestSubmit()`, because an input inside a shadow root has no form owner and implicit submission never fires. (2) A prop that shows an error also sets a `customError` validity, so the form blocks submission. (3) Only `aria-label` is forwarded from the host; `aria-labelledby` and `aria-describedby` are not, because ID references don't resolve across shadow roots.
**Why:** Each gap broke a promise in the contract while every test passed; the tests now cover all three.
**Watch out:** Enter submits without a submitter, so a ds-button submit's name/value is not sent on Enter (logged as Input drift).
