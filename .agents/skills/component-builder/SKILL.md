# Build a Sketchbook component

1. **Validate the inputs.** Read `harness.config.json`, the component's contract pair and `plan.md`, the API vocabulary and relevant decisions. If the contract is missing or has blocking questions, use `contract-author` and stop. If `features.planningGate` is enabled, verify the approval before writing tests, stories or implementation. Do not infer approval. Use existing components, helpers and tests as examples; ask before expanding scope into shared infrastructure or adding dependencies.
2. **Write the story and behavior spec from the contract.** When `features.testFirst` is enabled, run them before implementing and confirm failure for the intended behavior, not a broken fixture. Cover relevant props, variants, states, events, keyboard behavior, focus, accessible names and form behavior. Use the project's Playwright helpers and axe checks; check the screen-reader view for composite keyboard interactions. Don't rewrite passing criteria simply to match implementation.
3. **Implement the approved contract.** Follow the configured Web Component conventions: use native controls and the existing form mixins or focus controllers where applicable. Use one custom element per TypeScript file, declare compound parts in the contract, and use component tokens in SCSS. Alias component tokens to semantic tokens; add approved missing semantic tokens at the proper layer and declare applicable contrast pairs. Rebuild generated styles and exports with `npm run generate`; never edit generated outputs. Log any accessibility-driven deviation in the contract instead of silently changing the API or behavior.
4. **Verify.** Run `npm run check`, typechecking, lint and the relevant browser specs. Run broader harness and component gates when the change or release calls for them. Report blocked or skipped checks. If the contract itself is wrong, fix it first and get approval for any material scope change; do not make the tests fit the code.
5. **Review before beta.** Compare implementation to the contract: files, tags, props, events, parts, slots, states, tokens, keyboard/accessibility behavior and spec coverage. Use the [parity review brief](agents/parity-auditor.md) with a separate reviewer when available and authorized; otherwise report the parity review as pending and identify any self-checks performed. Record evidence and drift under web realizations; promote only after required checks and parity review pass. Keep contract and registry lifecycle status in sync. Stable requires the separate accessibility audit. In the Sketchbook source checkout, verify the catalog, public demos and configured design outputs using the maintainer workflow; installed projects follow their own documentation and design configuration.

For form controls, use `src/mixins/form-associated.ts` and `src/mixins/native-control.ts` with an existing input as a reference. Verify implicit submission, reset and validity; an error prop must set `customError` validity, and ARIA ID references do not cross shadow roots. For roving keyboard focus, start with `src/controllers/roving-focus.ts`. For stories, use the contract helpers in `src/stories/contract.ts` where applicable. Check `spec/decisions/DECISIONS.md` for the rationale and project-specific exceptions.

Report the checks actually run, any observed test-first failure, drift, token changes, review status and remaining work. Do not commit or publish unless asked.
