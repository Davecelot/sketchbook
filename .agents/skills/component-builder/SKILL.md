# Build a Sketchbook component

1. **Validate the inputs.** Read `harness.config.json`, the component's contract pair and `plan.md`, the API vocabulary and relevant decisions. If the contract is missing or has blocking questions, use `contract-author` and stop. If `features.planningGate` is on, verify the approval before writing tests, stories or implementation: `npm run check -- --only=C4` must pass and the plan's frontmatter must have a `stage` past `plan`. Do not infer approval. Resume from the frontmatter's `stage`, `next` and `blocker`. Use existing components, helpers and tests as examples; ask before expanding scope into shared infrastructure or adding dependencies.
2. **Write the story and behavior spec from the contract.** When `features.testFirst` is on, run `sketchbook evidence red <name>` before implementing. Confirm failure for the intended behavior, not a broken fixture. Cover relevant props, variants, states, events, keyboard behavior, focus, accessible names and form behavior. Use the project's Playwright helpers and axe checks; check the screen-reader view for composite keyboard interactions. Don't rewrite passing criteria simply to match implementation.
3. **Implement the approved contract.** Follow the configured Web Component conventions: use native controls and the existing form mixins or focus controllers where applicable. Use one custom element per TypeScript file, declare compound parts in the contract, and use component tokens in SCSS. Alias component tokens to semantic tokens; add approved missing semantic tokens at the proper layer and declare applicable contrast pairs. Rebuild generated styles and exports with `npm run generate`; never edit generated outputs. Log any accessibility-driven deviation in the contract instead of silently changing the API or behavior.
4. **Verify.** With test-first on, record `sketchbook evidence green <name>` using the same spec and test setup as red. Never write `evidence.json` yourself. Run `npm run check`, typechecking, lint and the relevant browser specs. Run broader gates when the change calls for them and report blocked or skipped checks. If the contract is wrong, fix it first and get approval for any material scope change.
5. **Review before beta.** Compare implementation to the contract: files, tags, props, events, parts, slots, states, tokens, keyboard/accessibility behavior and spec coverage. Use the [parity review brief](agents/parity-auditor.md) with a separate reviewer when available and authorized; otherwise report the parity review as pending and identify any self-checks performed. With test-first on, run `sketchbook evidence ready <name>` after review. Record coverage and drift under web realizations; promote only after the required checks and review pass. Keep contract and registry statuses in sync. Stable requires the separate accessibility audit. In the Sketchbook source checkout, verify the catalog, public demos and configured design outputs using the maintainer workflow; installed projects follow their own documentation and design configuration.

For form controls, use `src/mixins/form-associated.ts` and `src/mixins/native-control.ts` with an existing input as a reference. Verify implicit submission, reset and validity; an error prop must set `customError` validity, and ARIA ID references do not cross shadow roots. For roving keyboard focus, start with `src/controllers/roving-focus.ts`. For stories, use the contract helpers in `src/stories/contract.ts` where applicable. Check `spec/decisions/DECISIONS.md` for the rationale and project-specific exceptions.

## Shared task board (opt-in pilot)

When the person asks for a shared task board for a new composite component or substantial edit, use the [task board template](assets/task-board.md). Keep it outside the tracked component files and leave the existing workflow unchanged. The board tracks ownership, blockers and evidence links. It does not prove approval, test results, or readiness. Skip the board for routine work.

Report the checks actually run, any observed test-first failure, drift, token changes, review status and remaining work. Do not commit or publish unless asked.
