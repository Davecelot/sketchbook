# Themes: Mode x Shape x Density

The design file switches look the way the code does, from the same tokens, so switching proves the token system. Three independent axes; any combination is valid.

| Axis | What changes | Values come from | Today |
| --- | --- | --- | --- |
| Mode | color roles | `brand.config.json` > `modes` | light, dark |
| Shape | `radius.*` | `harness/standards/radius.json` presets | sharp, soft (default), round, pill-heavy |
| Density | the 11 density-linked tokens: `size.control.sm`, `size.control.default`, `size.control.lg`, `space.control.padding-x.*`, `space.control.gap.*` | `harness/standards/density.json` presets | compact, comfortable (default), spacious |

Which tokens each axis owns is read from `spec/tokens/brand-links.json` (links whose source is `radius` or `density`; checked 2026-11-09: 6 radius tokens, 11 density tokens). Doc chrome (`space.inset.*`, `space.stack.*`) is not linked to density, so Density changes components only; Shape changes components and the doc chrome (radii); Mode changes everything. If chrome should also follow Density, link those tokens to the density family in `brand-links.json` rather than special-casing the renderer.

The values in the last column are read from the catalog; add a preset to the catalog and it becomes an axis value with no other edit. "Rounded", "regular", "relaxed" in conversation are the labels `round`, `soft` and `spacious`.

Combinations today: 2 x 4 x 3 = 24.

## How a value reaches the design file

```text
standards preset  --resolve-->  semantic token values  --push-->  theme (one per axis value)
(radius.json id)   (harness/standards/resolve.mts,    (tokens.mts payload)   switch in the tool
                    harness/lib/tokens.mts)
```

- A theme for an axis value holds only what that axis owns: the semantic tokens linked to its family (`brand-links.json`) and the foundation tokens its presets change (found by comparing the presets: for Shape the foundation radius scale, from its smallest to its largest step), plus, for Mode, the mode's `color.*`. It is generated by the harness from the preset through the same resolver and `spec/tokens/brand-links.json` the code build uses, so the design file and the code cannot disagree.
- A renderer never copies a number from a preset. If a value is wrong, fix the preset or the link, rebuild and re-sync.
- Foundation and component sets are shared by every theme. Themes sit on top and override.

## Modeling it in a tool

| Tool | Axis | Axis value |
| --- | --- | --- |
| Figma | a variable collection (`Semantic - Color`, `Semantic - Shape`, `Semantic - Density`) | a mode of that collection |
| Other | any "independent switch" the tool offers | its states |

If a tool allows only one switch at a time, build one theme per combination (24) instead and say so in `tool-mapping.md`.

## The Theme matrix page

Every library set under the corner combinations, side by side (SB-0088). In Figma a frame can pin one mode per collection, so each cell pins every theme axis collection to its column's modes; the Live column pins none and follows the page, so flipping the page's modes shows any other combination. `sketchbook sync theme-matrix` writes the pastes (rows split so each stays under the paste limit) and a read-back.

```text
+-- Page "Theme matrix" -----------------------------------------------------------------------------+
|  Doc "Theme matrix"                                                                                 |
|   Header   Definition: "Every library set under the {N} corner combinations ... Live follows ..."  |
|   Matrix                                                                                            |
|    Columns   Set | Live | Light.Sharp.Compact | Light.Sharp.Spacious | ... | Dark.Pill.Spacious      |
|    {Set}     name + one caption per cell | Cell | Cell (pinned) | ... one row per drawn set          |
|      Cell    background card, the set's representative variants as instances, stacked               |
+-----------------------------------------------------------------------------------------------------+
```
- Columns: Live, then every axis at its first and last value (Mode: Light, Dark; Shape: Sharp, Pill controls; Density: Compact, Spacious), 8 corners today. The values come from the theme axes, not from the renderer.
- Rows: every drawn library set (element sets included), in library order.
- Representative variants: the set's first non-state axis varied (Variant, Size, Orientation, Selected, Kind...), every other axis at its first value (Rest, False, None), at most 6. A single-variant set shows its one variant.
- Cells keep their rows aligned whatever the density, because the pins sit on the cells, not on whole columns.
- The full proof of values is the variables read-back below; the matrix read-back proves the pins and the instances.

## Proof

One unit is a combination: one mode of every axis collection (24 today: 2 Mode x 4 Shape x 3 Density).
1. `sketchbook sync verify` writes a read-only script; run it in the file (one call).
2. It resolves every managed variable for every combination by following aliases with that combination's modes (no canvas switching) and returns one digest per combination, plus a digest of each collection's variable names and any missing or extra modes (about 2 KB).
3. `sketchbook sync verify --ingest <file>` computes the same digests from the variables model. The model is proven equal to the spec for every combination by test F2 (the same engine as the code build: the brand with that Shape and Density preset applied, in that Mode, through `brand-links.json`), so equal digests mean the file equals the spec. A differing combination fails D1; `sync verify --detail "<combination>"` returns that combination's values so the next ingest names each differing variable.
4. Screenshot the Theme matrix corners for the eye test.

Pass = no mismatch in step 3. A mismatch is reported with its combination; the design file is never patched by hand.
